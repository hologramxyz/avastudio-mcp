# HyperFrames traps for build.py films

- **Chrome sandbox on restricted Linux VMs:** capture and check use Chrome's sandbox by default. If Chrome reports `No usable sandbox`, use a machine with a working sandbox, or explicitly set `CHROME_NO_SANDBOX=1` for capture and check on an isolated VM with trusted page content. Root execution already requires this fallback. Do not disable the sandbox globally on a normal workstation.
- **Render with `render.sh`.** It makes one plain render: 1 worker with a GPU (Metal, or NVIDIA on Linux), one worker per core but one without. Never split a film with `--start/--end`: that path always draws in software (SwiftShader) and loads the page again for every chunk. `--browser-gpu` is on by default when Chrome finds a GPU (Metal on a Mac); the GPU frames differ from SwiftShader by about 52 dB PSNR, so render the frames you compare the same way. It sets `HYPERFRAMES_RENDER_LOCK=off` (else one render per user) and `HYPERFRAMES_RENDER_DETACHED=1` (else the render aborts with `render_cancelled_parent_exited` when the shell that started it, such as ssh, closes). Run it in the foreground. If you must detach it (`setsid nohup ... > log 2>&1 < /dev/null &`), end the command with `; echo done:$? >> log` and wait with `until grep -q '^done:' log; do sleep 5; done`. Never wait with `pgrep -f`: it matches its own loop.
  - Usage: `render.sh <project dir> <out.mp4> [fps: must match the build] [quality=delivery] [workers]`.
  - Without `--fps`, HyperFrames renders at 30 fps, because the root has no `data-fps`. `render.sh` always passes the built rate.
  - Metal renders with 2 or 4 workers lost the end line on every 2nd or 4th frame in 3 of 6 renders of one film. `qa.py` lists those frames under one-frame flashes (a frame whose brightest pixel drops below half of both neighbours'), and `render.sh` renders again without the GPU when it finds them.
- **Films with `<video>`** render with screenshot capture (`render.sh` sets `PRODUCER_FORCE_SCREENSHOT`): beginframe capture lost the page for long runs under parallel load.
- **Quality:** `delivery` for anything sent. It holds dark gradients far better than `draft`.
- **Render a window:** build only the shots you changed with `build.py ... --window <a>,<b>` and render that project. Its frames match the full render at the same times (58 dB or more; only the encode differs), so `splice.py` can put it back into the film.
- **Snapshots:** `hyperframes snapshot --no-end --at 1.2,10.3` writes frames and a contact sheet to `.hyperframes/artifacts/snapshots/<id>/`. Delete that id afterwards by its full path; never delete `.hyperframes` itself. A snapshot seeks straight to a time, so it can hide what a render shows: check every cut and entrance in the rendered file (`qa.py`).
- **Lint on a captured page:** warnings from the page's own CSS transitions, local fallback fonts and negative z-index are noise (43 on one page). Errors are not.
- **Gradient text:** Chrome drops the text clip of a multi-layer `background` shorthand, and the capture writes `background-clip` again. Still compare a snapshot of any gradient headline with `page.png`: a solid box behind the word means the clip was lost.
- **Fonts:** text whose class is missing falls back silently to the parent font and size. Read text in full-size snapshots, not only in contact sheets.
- **Disk:** a delivery render keeps about 2.3 MB per frame in the system temp folder while it runs, so a 40 s film at 60 fps needs about 6 GB free.
- **Stopping a render:** stop `render.sh` itself (Ctrl-C or `kill`).
- **Gemini upload:** inline video above about 20 MB fails. Review a 720p proxy (`scale=1280:-2`, crf 30).
- **Animated images:** animated GIF, animated WebP and SVG animations run on their own clock, not the film's. `build.py` keeps a GIF's first frame and names any animated WebP or SVG file, which you must replace with a still. Animations inside the page's own inline SVG are paused and played on the film's clock.
- **Page videos:** with `page.videos`, every captured video (MP4, WebM, MOV) plays again as an MP4 loop. One that ffmpeg cannot read stays a still, and `build.py` says so.
- **Fonts:** `build.py` drops repeated `@font-face` rules and the families that neither the page's CSS and markup nor the spec names. One page went from 4,320 rules to 84 with the same frames. Keep a family the CSS names even if no text used it at capture: without its `@font-face`, the HyperFrames compiler looks the name up as a font to fetch, and a snapshot of one product page hung.
- **Busy pages:** the capture waits for the page to load and then up to 20 s for its network to settle, so a page that keeps polling still captures.
- **Tall pages at high zoom:** a page about 9,000 px tall zoomed above about 1.8x passes Chrome's layer size limit (about 16,000 px) and paints nothing. Hide the sections a shot does not show (`display:none` in the spec's page CSS).
